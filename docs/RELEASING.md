# Releasing hiveField Terminal

Releases are produced by [`.github/workflows/release.yml`](../.github/workflows/release.yml).
This document covers how versions are managed, how to cut a release, and what
the workflow publishes.

## Version model

The app version is **single-sourced** across three files:

| File | Field |
| --- | --- |
| `package.json` | `version` |
| `src-tauri/Cargo.toml` | `[package].version` |
| `src-tauri/tauri.conf.json` | `version` |

`src-tauri/Cargo.lock` is rewritten too so a fresh `cargo build` never reports
a dirty lockfile. `.github/workflows/test.yml` runs
`bun scripts/version.ts check` on every push, so a hand-edit that leaves one
file behind fails CI instead of producing a mis-versioned release.

Never edit the version by hand. Use the script:

```sh
bun run version:show          # print the current version
bun run version:check         # verify every file agrees
bun run version:bump patch    # also accepts minor, major, or an exact x.y.z
```

The bump is a normal commit. Merge it to `master` when it is ready; the next
release picks it up.

### Tags and the embedded build number

Two kinds of tags exist:

- **Build releases** — `v<version>-build.<run_number>`, minted automatically on
  every push to `master`. The CI run number is embedded in the binary through
  `HF_BUILD_NUMBER`, so the built-in updater compares the exact build it came
  from (`0.1.2-build.12`) with the release tag.
- **Clean releases** — `v<version>` (for example `v0.2.0`), used for a
  deliberate, manually triggered release. No build number is embedded, so the
  binary reports exactly `0.2.0` and matches its tag.

The updater's version comparison treats a missing component as zero, so
`0.2.0` < `0.2.0-build.1` < `0.2.1`. A clean tag therefore does not get
overwritten by an older series.

## Cutting a release automatically

Merge to `master`. The workflow:

1. validates the version files and the tag;
2. runs the full test workflow on the exact commit being shipped;
3. builds Linux, macOS (x86_64 + aarch64), and Windows artifacts;
4. generates release notes with `git-cliff` from the commits since the
   previous tag;
5. publishes one GitHub release containing every platform's artifacts.

No manual tagging is required. `HF_BUILD_NUMBER` is set to the run number.

## Cutting a release manually

Use **Actions → Release → Run workflow**. Inputs:

| Input | Meaning |
| --- | --- |
| `version` | Exact version to release (e.g. `0.2.0`). Must match the checked-in version. Setting it produces a clean `v<version>` tag. |
| `bump` | `patch`, `minor`, or `major`: bumps the version, commits it, pushes it, and releases the result. Mutually exclusive with `version`. |
| `tag` | Explicit tag override (useful for re-running a release or using a prerelease tag). Must match the version, optionally with `-build.<n>`. |
| `dry_run` | Builds and tests everything but skips publishing. Cannot be combined with `bump`. |
| `prerelease` | Marks the published GitHub release as a prerelease (excluded from the updater's `latest` query). |

The `bump` input commits with `chore(release): v<version> [skip release]`.
That push triggers the workflow again, but the `[skip release]` marker makes
the second run skip immediately. Run manual releases from `master`.

## Changelog

Release notes are generated by [git-cliff](https://git-cliff.org) using
[`cliff.toml`](../cliff.toml):

- `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `style`, `chore`, and
  `ci` commits are grouped;
- non-conventional commits are kept under **Other changes** (this repository
  has many, and dropping them would hide real work);
- merge commits and `chore(release)` bump commits are skipped;
- commits are listed oldest-first.

Write conventional commit messages where possible to get useful grouping, but
a non-conventional message is never lost.

## If a release fails

- **Version/tag mismatch** — run `bun run version:bump <kind>`, merge to
  `master`, and retry. The error names the expected version.
- **Tag already exists** — pass an explicit `tag` input or bump the version.
- **Build job failed** — re-run the failed jobs from the Actions UI. The
  `publish` job only runs after all three platform builds succeed, so a failed
  build never publishes a partial release.
- **Publish failed after the tag is live** — re-run `publish`; the release is
  updated in place with the same body and assets.

A failed run never creates the remote tag: the publish job creates the tag
locally only to compute the changelog range, and `softprops/action-gh-release`
creates the real tag last.

## Building locally

```sh
bun run tauri build
```

Outputs are in `src-tauri/target/release/bundle/`. Local builds have no
`HF_BUILD_NUMBER`, so the app reports the plain `CARGO_PKG_VERSION`.
